# 常见陷阱与路径模拟决策
> 2026-09-20 外迁自 SKILL.md v1.4.2（原文逐字保留，未改写）。

## 陷阱

| 陷阱 | 为什么是问题 | 正确做法 |
|------|------------|---------|
| patch 报 no_change 就以为删了 | fuzzy match 可能误判"目标已存在"，实际残留段还在 | 改后必须 python/read_file **重读目标段确认**，不信 no_change（2026-08-08 实测第一次 patch 就误报，重读发现残留段原封不动，换精确 old_string 才删掉） |
| 删错位文件前不查独有信息 | 文件里可能有别处没有的规则 | 删前在你的知识库/参考库全文搜索 + 查目标 skill，独有内容先归位再删 |
| 只修 SKILL.md 不修 references | 孤儿文件继续躺着，读者翻不到 | 补链接或删除二选一，别留半吊子 |
| 残留段带未闭合 \`\`\` 以为无害 | 后续整节渲染成代码块，阅读直接坏 | 代码块配对检查必做 |
| read_file 读含 VS 的文件报 Binary 就放弃 | Unicode variation selectors 误判，文件本身正常 | python3 读，grep 不受影响可辅助验证 |
| 信 references 里的「X 文件第 N 行规定 Y」 | 声称的权威可能不存在或行号不对（实测 SOUL.md 第22行是「删除文件前必须问」，却被声称是 10k 上限） | 逐条 grep 验证声称；真权威常是 config.yaml 而非 SOUL.md |
| 兜底写在文件尾部、入口无前向提示 | agent 走到触发点不知道有解法，可能卡住 | 触发点加「若报 X，见异常表第 N 行」；检查入口与兜底距离 |
| 文档说 JSON 工作流、脚本只吃 HTML（或反之） | doc/script 割裂，读者照文档走脚本报错 | 脚本改读文档格式，或文档改回脚本真能吃格式；不准留「注：当前版本基于 X 格式」兜底把缺陷写进文档（2026-08-09 实测 dia-bookmark-sync） |
| read_file 报 Binary 就当真二进制放弃 | 纯中文 UTF-8 也会误判，文件本身正常 | 先 `file <path>` 看是否 UTF-8 text，是则用 python3 读出，grep 不受影响可辅助 |
| 只跑 8d 变更关键词对账，以为跨文件语义打架查过了 | 8d 关键词表 = 本轮改造的旧词（grep 仍是全目录），历史轮次留下的旧口径不在本轮关键词集里，deep 文件永不命中（2026-09-16 实测：某多文件 skill 四轮验收全绿 vs 同日全量深读抓 3 处判据打架） | 全量档跑 8g：跨文件重复判据逐对双向核方向，不依赖本轮变更关键词 |
| 架构改造后只验主干路径，不查旧口径残留 | 旧表述/旧标注/旧说明文字残留在漏改位置（双模式改造实测 3 类：触发句还写「走完整审计」、3 处 CHECKPOINT 只标 2 处、query 加了 sort 但说明还写旧语义），路径模拟走主干抓不到 | 改造后先做 8d 旧口径对账：列旧关键词全目录 grep + 同款元素逐个核对标注，再跑路径模拟 |
| 评估"会不会好用"只看结构 | 结构健康 ≠ 体验好 | 对用户本人极好用 ≠ 对外人好用：还要查私有依赖（MCP/用户名/硬编码路径）、私有上下文（"本会话实测"时间戳）、单一用户假设 |
| 外迁后只扫路径引用，不扫散文指路语 | 「见第 X 节」「第 N 条」「见 Step 5」不是引用语法，第 2 步 grep 与脚本都扫不到；目标被搬走后执行者顺指路语翻不到内容（实测：10 skill 瘦身后扫出 4 处悬空指路，路径层当时全绿） | 外迁改动后跑 2c 的指路语 grep，逐条核对目标是本文件还是已外迁；已外迁的改成显式文件链接 |
| 外迁附则时顺手删掉了附近旧引用语句 | 替换节为指向行的操作会波及周围文本，产生新孤儿（2026-08-28 实测：某多文件 skill 瘦身后 5 个 references 断链） | 外迁后必重跑第 2 步孤儿检测；新指向行的措辞要覆盖原引用的信息量（指向行丢失「见异常表第 N 行」这类细节=兜底前向引用退化） |
| 指向行声称「见 X 文件的 Y 条目」但 X 里没有 Y | 外迁/重组时指向行凭记忆写，目标文件实际条目名对不上（2026-08-28 实测：④写「日期过时→date」，pitfalls.md 无此条，真身在 common-pitfalls.md） | 写指向行前先 grep 目标文件确认条目存在；跨文件指向优先指向条目真身而非就近文件 |
| 同名 skill 两份，删文件后总再回来 | hub 管理的 skill 按 lock.json 登记路径复种；删副本前先 grep `~/.hermes/skills/.hub/lock.json` | lock.json 登记的走 `hermes skills uninstall`，未登记的直接删文件 |
| 把仓库体量或 star 当 skill 复杂度 | 分发适配器会让仓库看起来很重，canonical 文件可能只有一百行 | 体检只打 canonical SKILL.md（见 8f）；star 是分发信号，不是结构分数 |
| 散文落点路径核不到（8d 同族） | 正文句子里的「产物存到 `<某路径>`」「归档到 X 目录」不是引用语法，第 2 步的孤儿/断链检测天然扫不到 | 把路径拿到真实磁盘 `ls` 核对存在性；同动作在姊妹 skill 有另一种写法时先对比口径，两边矛盾必有一假（2026-09 本地版实测沉淀） |
| 引用检查把跨 skill 指向报成断裂 | 正文提及别家 skill 的 references 路径会被本目录引用检查误判为断裂 | 2026-09-22 起脚本自动识别为 `ℹ️ 跨 skill 引用（非问题）`（全库查正主、不影响退出码），**不必再逐处改措辞**；措辞消歧法已废 |
| 姊妹 skill 动词/硬数字越界 | description 开头动词用了姊妹 skill 的职能词（体检清单写「发布前验收」），模型分不清触发词归属谁；消费方抄步骤总数硬数字（「十步清单」），源加一步消费方就成了现行犯且路径模拟抓不到 | description 用本词表述职能、句尾带一句责任边界（「只管 X；整体验收走 Y」）；消费方只引用步骤号不写总数硬数字。**清单步骤增删即全家福对账**：grep 全库引用本 skill 的 SKILL.md，同步消费方措辞与其降级快照表行，一次改齐再收工 |
| 报「缺 X 项」类断言凭印象/局部读下结论 | 验收报告声称目标缺某行/某节，实际存在（只扫了部分表就断言全缺）——假缺陷进报告后用户照单全收去修，修空气比漏修更伤信任 | 每条「缺失」断言落报告前先对该目标 grep 一次拿命中/零命中作证据（存在性断言的举证责任和断裂检测对称：说「有」要引原文，说「缺」要贴零命中命令输出） |

## 体检后：要不要跑路径模拟？（2026-08-08 定稿）

**结论：只要被测 skill 是「用户会走一串步骤」的流程类 skill，就值得跑一次 path-simulation——高频实战不是豁免理由。**

曾误判：「某多文件 skill 是你最高频实战的 skill，每次你说整理记忆就是真实走一遍，实战即模拟，不需要专门路径模拟。」用户坚持跑了一遍，**立刻抓到 2 条实战暴露不了的问题**（虚假权威引用、兜底无前向引用）——都是「跨文件路径 #7」才看得到的：

- 实战走主干：通读→决策→执行，永远不会去核对 references 声称的权威是否真实存在
- 路径模拟走跨文件路径：专门 grep 所有「X 文件第 N 行规定 Y」声称 → 发现 SOUL.md 引用是假的

**正确的判断框架**：
- 高频实战 skill：主干路径早已被真实执行验证过，**但跨文件一致性从未被验证** → 至少跑一次跨文件路径 #7（专核 references 之间、references 与外部权威之间的矛盾）
- 低频/未发布 skill：跑标准 + 风险路径全套
- 纯知识类（无步骤）：不跑，静态检查够

## 引用型断言的自伤陷阱（2026-09-22 增量验收实测）

- **拿 mtime 当证据 = 自伤型断言**：写过「本文件 mtime 与 X 时刻逐秒吻合」这类句子，**写下它的动作本身就改了 mtime**，同一行断言当场失效（实测：curator 21:07:02Z 写入 → 人工补写来源说明后 mtime 变 21:27:19Z，注释里的吻合声明随即变假，下一轮验收直接判为「权威声称已失效」）。**规则：来源/版本类声称一律用 sha256 锚定**（账本行 `after.sha256` + 现行文件 sha 并列），必要时补「现行版由谁在何时改过、是否在账本内」。
- **断言词不要出现在夹具内容里**：自测断言写 `"超限" in out`，而夹具的 description 文本自带「超限」二字被预览打印 → **假通过**。断言要精确到信号词（`"🔴 超限"`）或退出码，夹具内容也要避开断言词。
- **负例夹具必须符合被测格式**：夹具里把「孤儿」文件写进正文引用，它就不再是孤儿——断言失败会被误读成脚本 bug（实测本轮假阴性 2 次）。造负例前先确认「这个对象在被测口径下真的是问题」。
- **改完任一脚本先跑 `scripts/selftest.py`**：20+ 条断言 0 成本回归，别靠临时夹具重复劳动。**断言条数随回归点增删，任何地方都别写死具体数字**（2026-09-27 实测：文档写 19、实测 21，同款错第三轮复发——真值是脚本的 case 调用点，B2 的循环每次调用都算一条）。
- **写死计数 = 把内容状态当内容事实，必然漂**（本 skill 自己的复发形态，2026-09-27 三仓各命中一处）：本 skill「19 条断言」、姊妹仓「现 9 坑」「8 条路径」、本轮新写的「现 26,507 字符」在通用化发布副本里变 26,932。**关键性质是它假得毫无症状**——读起来通顺，只有增删内容时对照才发现，比断链更难发现（断链至少有 grep 入口）。**判据**：「这个数在声称当前状态」→ 删掉改指向实体（枚举本身在就有信息量，数字纯冗余）；「在陈述过去某刻的事实」（如「2026-08-28 实测 7 个问题」）→ 不动，改了是篡改历史。**别把判据阈值误当计数**：「至少走 3 条」「附则 >40% 才外迁」写死是对的，那是规则本身。**防复发**：被引文件（references/）的标题与开篇也不写自己的条数——最常见的复发形态是正文改概括式了、references 标题里的「8 条」忘了改。

与 `path-simulation` skill 的衔接：体检第 7 步（权威声称核实）就是跨文件路径 #7 的具体化，8g（全量判据对账）是 #7 对账方法的权威版（#7 执行定义已回指，两文件均独立可用）；跑路径模拟时直接复用本 skill 的清单。

## 多轮修同一 skill：自写回归不是证据

### 自写回归全绿 ≠ 验收通过

自己写的回归用例是**照自己的实现意图**造的；实现有偏差时**用例与偏差同源**，绿是恒真的。实测：某 skill 连修三轮，每轮自写回归全绿（15 组 flag 组合 + 19 项断言），独立对抗验证一轮抓 9 个、下一轮又抓 6 个——**自写回归一个都没抓到**。第 9 步「正例+负例+回归」三件套能验「检查器没被改坏」，验不了「判据本身选得对不对」。

**防法**：收尾前另走一轮**独立对抗验证**（派子代理只找 bug 不修）。派单必须写死三条：①**禁写真实系统**——需改磁盘数据时用 `HOME` 指向临时目录，并**按被测脚本的完整依赖清单建齐文件**（只建主文件不建次级文件会得到无法解释的输出；见 8g 形态 7 末段的无路径参数陷阱）②**清 `__pycache__` 或带 `PYTHONDONTWRITEBYTECODE=1` 跑新进程**——`import` 会吃缓存，症状是「read_file 读到新文件、Python 跑的是旧行为」，会误判修复无效（这个坑值得单独说：它同时污染主会话与子代理，两边都可能得出「改了没用」的错误结论）③发现被测文件中途被改要如实上报——子代理发现并上报并发编辑，比多报一个 bug 更有价值。

### 故障注入：主动构造「该被抓到」的输入，去找检查器放行的地方

上面两条讲的是**让断言能变红**（别造恒绿的假绿）。这条是它的反面动作，且独立有效：**造一批已知该被拦住的输入，逐个看检查器报什么**。判据不是「有没有输出」，是**报的等级对不对**。

实测一次故障注入，在自写回归 14 项全绿的情况下抓到三个**共同形态**——本该报警时静默放行：

| 注入 | 静默行为 | 为什么静默 |
|---|---|---|
| 目标文件被清空 | 头部校验打 `✅ 全部条目头合法`（0 条 = 0 个违规）、末行 `exit 0「机械项通过」` | 存在性检查过了（文件在），后续每道检查都把「空」当「无问题」 |
| 上限配成 `0` | 当成 1 → 永远 100% 过线，越线判据形同虚设 | 解析层 `max(x, 1)` 静默吃掉非法值 |
| 上限配成 `-5` | 回退默认值 → 容量恒 0%，越线检查全失效 | 正则 `(\d+)` 不匹配负号，匹配失败与「键不存在」同路径 |

**共同形态比单个缺陷更值得记**：三者都不是「少写了一个分支」，而是**失败被下游当成成功**。查这类缺陷时按形态找——「什么输入会让本该失败的路径走进成功分支」，比逐个 flag 试快得多。

**绿灯的语义**：一条检查项的绿，含义是「**它测过会红**」，不是「它跑过了」。二者不等价，且前者要靠故障注入担保。跑一百遍全绿而没喂过一个该红的输入，等于没验。

### 刚写完的守卫，是全场最可疑的东西

修完缺陷立刻收工是最常见的收手过早。**新写的守卫自己就有绕过路径**，而你自己的测试清单里不会包含你没想到的那个形态——实测第一版判空守卫（`strip()` 后为空即拦）漏掉两种：

- 只剩分隔符（`§\n§\n§`）——非空，放行
- 只有 BOM（`﻿`）——非空，放行

⚠️ **派子代理做对抗验证替代不了自己动手**：子代理测的是**你给它的清单**，你清单里本来就没有 BOM，它大概率同样漏（除非任务书要求它自行枚举残骸形态）。派单可以补位，不能代替「写完守卫立刻逐个残骸形态手工复测」这个动作。

### 判「内容是否为空」别直接复用现成的切分函数

复用是把双刃：省事，且**把切分函数自己的过滤盲区一并继承进来**。实测拿现成的条目切分函数判空——它把单独的 `'\ufeff'` 算成**一条有效条目**（非空、且不以 `#` 开头，两个过滤条件都过），于是「BOM-only 文件」被判成有内容。

**判据：复用前先问「这个函数的过滤条件会不会放行残骸」**——单个 BOM、孤立分隔符、章节标题残留都能同时满足「非空」和「不以 # 开头」。正确做法是**先剥残骸再数**（`raw.strip().strip("\ufeff# \t\r\n§")`），而不是直接数。

同族：任何「用 X 的返回值当有效性判据」的写法，都要确认 X 对**退化输入**的返回值——正常输入的返回值从不骗人，退化输入才会。

### 「判有无」的守卫不拦「剩一点」——完整性要两条独立判据

守卫写成「有没有一条合格内容」时，它对**归零**敏感、对**断崖**完全失明。实测：62 条掉到 3 条、每条都内容完整，全部通过「有内容」校验，末行报「通过，可继续」——比清零更隐蔽、后果同样严重。

**根因是判据只回答了「非空吗」，没回答「够不够」**，而这两个是不同的失效。

**防法：完整性守卫必须两条独立判据。** ①**绝对**：有没有合格内容（防清零）；②**相对**：与已知好状态比，跌幅是否超阈值（防断崖）。

两条判据的**量纲不能混**：
- **绝对判据用体量**（单条实质内容 ≥ N 字符）——绝对体量没有跨用户通用安全值。
- **相对判据用跌幅**（当前条目数 < 基线的 X%）——跌幅才是可跨用户、跨阶段比较的量。**不要用绝对条目数当红线**：每人的库大小不同，同一个数字对 A 是正常、对 B 是灾难。
- **无参照时不判**：无基线/首跑时相对判据无从比较，此时只跑绝对判据，**不拿绝对值硬凑红线**（宁可漏报也不误杀）。

配套：**新判据要在旧判据之前生效**。实测把新判据接在「写回基准」之后，塌陷态就已经写进基线了——之后永远「一致」，最坏情况从「检测不到」变成「结构性检测不到」。**先阻断、再允许写参照物**，顺序反了会让后续所有轮次都继承那个坏状态。

### 「有 N 个用例」不证明阈值被测到——覆盖只能靠变异测试证明

阈值的覆盖有两个问题：**用例可能全在阈值两侧远处**（负例都远低于、正例都远超），中间整段区间零覆盖；**同一个数字可能在多处硬编码**，改一处不同步另一处。两者的症状都是**没有任何测试会红**。

实测：某阈值有 7 个用例，变异测试把它从 16 改成 4（用了新值）**自测仍 100% 全绿**——而该阈值下方的一整段区间正是一个真实误杀区。

**防法**：
1. **阈值/边界类断言必须逐值扫过临界区间**（如 1..20 全跑），不是补几个代表值。判据：把阈值改成一个**新值**（不是改坏，是换个邻近合法值）看会不会红；不会红就是区间没覆盖。
2. **同一语义的数字只允许有一处定义**（具名常量），不得在第二个目标里硬编码。给新目标加守卫时，**先问「它和原目标是同一种东西吗」**——不同质就各用各的判据；相同质就复用常量，不要复制数字。
3. **变异测试要当收工项跑，不是想起来才跑**：每次修完守卫/判据，把该判据改回旧值或改成邻近值，确认自测转红再收工。没转红 = 断言是装饰。

### 阈值语义要问「这个数字代表什么」，而不只是「多少」

同一个数在两处可能是两种含义，跨目标照搬会误杀。实测：体量阈值「≥16 字符」对条格式内容是「够不够像一条内容」，对散文体内容却是「够不够长」——后者会把语义完整的短文件（如一句话的身份定义）报成「被清空」并阻断整轮。

**防法**：定阈值时先写一句「这个数字在**这个目标**上代表什么」，与原目标的语义对不上就换判据。同族问法：判据要问「**空**还是**短**」——两者都是异常，但只有前者该被当事故阻断。

### 判据要问「够不够像内容」，不能问「像不像残骸」

守卫最常见的结构性失败是**枚举残骸形态**——列了 0 字节/纯空白/只有分隔符……然后被没列到的形态穿过。**形态枚举是无限的，形状特征是有限的**，补不完。**体量是连续量，一刀切**；形状是离散枚举，永远漏。

判据往往要三版才对，每版被下一版推翻（实测同一条判据的三次迭代）：

| 版 | 判据 | 漏什么 |
|---|---|---|
| 1 | 非空即有效 | 只有分隔符、只有 BOM（都非空但零内容） |
| 2 | 用现成切分函数判「零条目」 | 切分函数**自己**把残骸当条目（见上节） |
| 3 | 有实质体量的条目 | 形态与体量无关，不漏 |

**每版都要过完整故障注入矩阵才能宣布完成**，别在第一版就收工。判据推翻前序版本是正常演进，不是白工。

### 判据不能跨体裁照搬

同一套切分/判空逻辑对**不同体裁**的文件会给出相反结论。**条格式**（固定分隔符的条目流）与**散文体**（自然段、标题层级）必须各用各的判据：条格式按「有效条目数」判，散文体按「去标题行后的正文体量」判。

实测：把条格式的判空判据直接用在散文体文件上，**一份 1,257 字的正常文件被判成空**。这不是假阴性事故，是**把守卫装反了**——它会长期对真实文件误报，直到有人手动绕过。

**加任何按文件判定的守卫前，先确认该文件的体裁**，再选判据。

### 「不存在」与「存在但空」是两件事

文件缺失往往是**允许的配置**（有回退默认、官方口径可选），而在却 0 字节是**内容丢失**。合并成一个判据会两头出错：要么对缺失误报，要么对空放行。

**加守卫前先查该文件在本系统里的定位**（可缺失？可空？有没有官方回退？），再决定判据，并把两种情形分开断言。设计判据时用「缺与空分别是什么」的表格先列一遍，比直接写 `if not exists` 稳。

### 断言写强不写弱：断「结论变了」，别断「含某字串」

| 弱判据（会自满足） | 强判据 |
|---|---|
| 「输出里含某字串」 | 结论行/退出码发生了预期变化 |
| 「没看到报错」 | 预期信号词精确命中（带灯标） |
| 「跑通了」 | 坏输入被拦 **且** 好输入放行 |

**字串判据极易自满足**：被测代码里**另一行**输出同一字串（改了措辞、换了分支、同一句被多处调用）→ 断言照样绿。实测删掉配置层的出声提示后断言仍判绿，因为命中来自另一行。**只有「结论变了」能穿透这种巧合。**

**绿灯的语义**（贯穿本节）：一条检查项的绿，含义是「**它测过会红**」，不是「它跑过了」。前者只能靠故障注入 + 变异测试担保。

### 正例夹具太脏 = 正例根本没被测到

加新守卫后自测大面积转红（实测 20 项挂 16）时，**先看夹具而不是先改守卫**：最常见是正例夹具正文短于新判据的体量下限。

⚠️ 后果不只是要修夹具：**脏夹具只测到「守卫拦住了垃圾」，正例完全没测到**——整套测试看着在跑，实际一半场景是空转。**每次给守卫加判据，正例夹具必须重写一遍**，且至少一档直接用**真实文件原文**（复制不改），只造破坏变体；造完立刻把新判据套在每档夹具上过一遍，全绿才继续。

配套：恢复/归档类夹具同理——恢复出来的内容必须过一遍**当前**判据，不能沿用恢复当时的判据。

### 「独立一轮没报出新问题」只在**一轮**成立

实测连跑 5 轮，每轮都报出真问题，且分布有规律：**每轮修的都对，但每轮都在边界/异常路径上开新洞**（假缺失↔假在位、漏报↔误报、红字改结论↔老路径复发）。把它当终止条件会无限循环；逐条追边界的收益在第 3-4 轮后拐向下行。

**防法**：**第 2 轮起换方法——按「判据类型」横切，不追单点边界。** 把被测对象的全部判据归成 N 类（如退出码语义、写回副作用守卫、分级判据、计数口径、边界匹配、用法误用、可叠加性），每类构造正例+异常+误用三态，产出「已核/未核」清单，**未核的必须列出**。横切的产出是「10/13 类全绿」这种**覆盖面结论**，比「这次没撞上」强得多——前几轮零散验证从未整体确认过。派单不要把「找新问题」当唯一目标；子代理报「全绿」时**要求它列出未核项**。

### 「能用对」与「好用」是两个验收面

四轮全在验正确性（退出码、判据、回归），可用性缺陷一个没抓到——因为默认「跑对就等于好用」。实测抓到的：常用路径 55 行输出、**判决（能不能继续）埋在最后一行**，每次要读满才知道结论；以及**给人看的条数与算账用的条数不同源**（展示 3 条、上限只算 1 份 → 按展示估收益高估 3 倍）。

**防法**：正确性验完后**另起一轮只测体感**——常用路径各跑一次，记耗时 / 输出行数 / **首行是否回答「我要不要继续读」**。判决依赖中途才填满的数据时**别硬前置**（会打出空结论，比不打更坏），退化成开头导航行（本次跑什么 + 判决在第几行 + 退出码速查），两处内容同源。

### 🔴 横切到全绿也验不到的一层：声明本身对不对（兑现性）

上面所有手段——独立对抗、按判据横切、正例/负例/回归——**验的都是「输出是否符合声明」**：格式对不对、口径一不一致、字段全不全、退出码对不对、边界行为对不对。**没一个验「声明本身对不对」，而缺陷恰恰全在这一层。**

实测：5 轮独立对抗 + 按判据横切收出「N 类全绿」之后，被另一个会话拿旧版跑了一次真实任务，直接量出：**输出「可压上限 4,310 字符」→ 实际兑现 33 字符，且预估方向是反的（估 -560、实测 +111）**。原因是那个数字实际是「待处置对象体量」，不是「删了能省多少」——差一个数量级，方向相反。脚本按设计工作，声明本身就是错的。

**为什么所有静态验收都照不出来**：夹具造的是符合声明的输入，跑出符合声明的输出，**闭环自洽**。你验的每一环都在证明「我做到了我说的」，从没问过「我说的对不对」。

**防法**：
1. **凡输出体量／上限／可用量／收益类数字，验收时做一次「拿这个数去兑现」的推演**——逐组问「这组真能省这么多吗，依赖什么前提，前提成立吗」。前提不成立（如「能否兑现取决于某项前置检查，而这一步流程里没串进来」）→ 该数字是**误导性产出**，阻断级。**改动通常不在算法，在前置流程少串了一步。**
2. **指标命名先问「这个词会不会被下游读成承诺」**。「上限/总量/可回收」会被直接当目标数字用，而它可能只是「待处置对象体量」。改法优先是**改名 + 显式标注三态**（这是上限／这是承诺／这是未知），让下游无法误读——数字本身往往不用改。
3. **凡数字进了预算表／容量账／报表旁，每行标明它属于哪一类**，三类不混在一张表里。
4. **把真实使用列为验收面**（最有效）：让被测对象跑一次完整真实任务，拿实际结果对账每个关键数字。**发现差异先怀疑声明层，再查实现。** 改完最好让**刚踩过坑的那个使用者/会话**复跑一次——他知道痛点在哪，是最灵敏的检验器。
5. **收工汇报分层报，不许只说「验完了」**：①横切的类目覆盖结论（已核 N/M + 证据）；②**单列「声明层未验项」**（哪些产出没被独立验证过能否兑现）；③剩余风险与建议的复验方式。**独立复验证不了「没有问题」**，不要向要这个承诺的使用者打包票。

### 展示数字与算账数字必须同源

凡是使用者会拿展示值做乘法的地方（条数 × 单条长度 = 收益），展示必须带去重说明。实测：三条完全相同的条目 → 展示「3 条」、上限按 `(标签,文本)` 去重只算 1 份，**按展示估收益高估 3 倍**，且该数字直进容量账与兜底预算。**判据：给人看的数与算账用的数是两套代码时，先问「人会不会拿这个数去算账」。**

### 改判据时 grep 实现处计数，不止改第一处

同一个判据常散落多处实现。实测：判据是「键可带引号」，函数里有两条独立正则各管一段，只改第一条 → 复验全红，**等于没改**。

**防法**：改判据时 grep 该判据关键词，**数一数有几处实现**；`≠1` 就逐处核。配套：**注释里凡是「已处理 X」的，必须能指出对应那几行代码**——注释与实现不符最毒，它让人（包括自己复验时）**误判「已修」**，真 bug 活到下一轮被当成新发现。

### 末行结论不能与正文矛盾

正文已正确区分「不可读（查权限/编码）」，末行结论仍写「确认是否被移动/改名」——**人只看末行就被指去错方向**。一个 skill 往往有多个对用户说话的出口（阶段结论、汇总行、末行），任一处改了其余都要跟着改。

**防法**：改任何一处用户可见文案，**grep 同一语义的其他出口**；每个出口都要能独立读懂。配套：前置校验要验「用得上」不只验「在」——只查 `exists` 时，权限/编码这类「在但读不了」会掉进通用异常分支被报成「工具坏了」，而它与「东西不在」是同一类问题，该给同一个可读报错。

## 有效性体检：检出率、诚实度、体面是三条独立轴

本节管**「这套检查/审计机制在真实数据上真能抓到东西吗」**——与前面的结构体检（文件/引用/格式）互补。结构全绿与有效是两个结论，**不能互相顶替**。

### 三个必须分开的轴

| 轴 | 含义 | 怎么验 | 容易混淆的报法 |
|---|---|---|---|
| **检出率** | 原来抓不到的，现在能抓到 | 拿**真实缺陷集**量命中率 | 说成「变聪明了」 |
| **诚实度** | 声明与能力对齐 | 比对声称 vs 实现 | 说成「更能干了」 |
| **成本/体面** | 更短/更快/更整齐 | 量体积、耗时、调用数 | 说成「效率提升」 |

**减法型改造（合并模式、剥日志、移文件到别的 skill）几乎只动后两条轴，检出率零变化。** 用户问「确定改完真能到位么」而你手上只有减法方案时，**如实说「这不提升检出率」**——把体面改善答成能力改善，会让用户以为病灶被治了。

### 提删任何能力前：查调用量，不看行数占比

**体积占比是最容易骗人的指标。** 实测一个 1,255 行的检查器：按「核心层 194 行 = 15% / 邻接层 668 行 = 53%」的算法，会得出「砍掉那 53%」的结论；而那 53% 里包含了唯一一个「防止使用者误以为能自动判定」的诚实检查器。

查真实调用（**工具调用落在消息的 `tool_calls` 列，不在 `content` 里**——只查 content 会得到假阴性）：

```bash
sqlite3 ~/.hermes/state.db "select timestamp,session_id,tool_calls from messages
  where tool_calls like '%<脚本名>%' order by timestamp;"
```

解析出每个 flag 的调用次数后，**必须再按日/按会话分组**。实测：某组 flag 20 天内被调 100 次，看着像「高频常用」；但按日分组后发现**调用全部集中在同一天**，且会话标题全指向该工具自身的开发/验收——**是开发调试，不是真实使用**。

**判据：调用次数要按「排除该工具自身的开发/验收会话」重算，剩下的才是真实使用率。** 直接拿总数当「常用」证据，会把开发期调试当成日常依赖，据此做出「不能砍」或「该砍」的错误判断。

### 报检出率前：逐条核实你植入的缺陷真的存在

拿真实缺陷当标准答案量命中率是有效手法，但**标准答案必须先验明**。造完「已知缺陷」清单后逐条 grep 真实数据——实测 5 条里 **2 条查无此事**（记的是「某实体在两处重复出现」，实际一个文件 0 次、另一个 1 次，根本没重复），**这两条必须从分母剔除**。

**这一步同时是自我欺骗的照妖镜**：清单里若有「我以为存在」的缺陷，说明**你并不掌握真实基线**——此时无论算出什么命中率都不成立，汇报出去就成了编造的数字。实测剔掉无效靶子后：真实缺陷 3 个、命中 1 个，**命中率 33%**；若把编造的 2 条算进分母，就会报成 40% 的漂亮数字。

**判据：报任何命中率前，先把「标准答案清单」每条的证据贴出来（grep 命令 + 命中数）。** 说不清就降级成「待确认」，别让用户照单全收一个没核实过的分母。

### 双副本互校：对「同时更新两份」结构性失明

用两份文件互相校对以发现「谁被偷偷改了」（基线文件 vs 日志末条互校、分叉检测），**机制上只能发现单边更新**。当一次正常操作同时改了两份（写回流程一次追加两处），两份恒等 → 检查永远沉默。

**而这恰恰是最该被发现的情形**：实测一次「基线被非审计方重写」——审计方自己走正常写回流程时同时更新了两个文件，分叉检测零告警，工具报「一致 ✅」。

**判据：问「这个检测器在什么情况下必然沉默」**——沉默态就是它的盲区边界。报「无法检测某类改动」时必须标明**这是结构性的还是没查**，否则「检测器没报」会被读成「没有这类改动」。

### 把「诚实的不可能性」当成冗余，是体检最容易犯的错

一个检查器对真实数据全部返回「无可比信息，靠人工判断」——看起来像坏掉的空壳，**但它是全套机制里最诚实的一块**：它拦住使用者误以为该判断已自动完成。实测：4/4 真实条目都返回「无硬事实」；而同族的其它检查在同样的真实数据上，少数返回精确结果、多数返回噪音（喂通用词得十几处无效命中，喂精确实体得两处可直接定案）。

**「返回空」与「没实现」在输出上无法区分，必须主动证伪。** 判据：

- **别按返回率判死活**——返回「算不了」的检查器可能比返回精确数字的更可靠，后者才需要追问「这个数字能兑现吗」（见上文兑现性一节）。
- **别因为它不产出数字就当它冗余**——它的产出是**边界**（让流程在该转人工处转人工）。删掉它，流程会静默地把不可判定的交给下游当作已判定。
- **区分「诚实报空」与「静默失败」**：前者有明确措辞引导下一步（写明「靠通读/靠人工」），后者是无声返回空——**只有前者是设计，只有后者是 bug**。
